# Workflow acceptance scenarios

Maintainer regression fixtures, not an additional agent rulebook. Evaluate using only the installed AGENTS/ADB/START files and the scenario's project context. These checks assess decisions separately from script/layout tests. Record the actual outcome and capability limits; a static word match is not behavioral proof.

| Scenario | Required outcome |
|---|---|
| Empty app: user requests a simple calculator with a PIN and selects ADB | Clarify material behavior and obtain scope approval; no invented approval from method selection |
| Existing approved ADB app: fix a specified typo | MainAgent can act directly and self-check; no repeated interview or forced subagents |
| User approved an exact plan earlier, then says start | Reuse recorded authorization and execute within scope |
| User delegates appearance within accessibility and product constraints | Choose within those limits, record provenance; no expansion into unrelated features |
| New user instruction contradicts old product docs | Update affected scope from the explicit instruction; status cannot restore the obsolete decision |
| Review finds a required journey broken, labels impact MEDIUM | FAIL and concrete repair; no PASS WITH ISSUES for broken mandatory behavior |
| Fix changes behavior of another state | Recheck the affected state and existing promise; obtain a scope decision if changing the promise |
| Plan review before product code exists | Evaluate scope, feasible checks and risks; no full duplicate implementation required |
| Small display change in a payments product | Classify this change, permit self-check |
| Permission logic change, no separate reviewer available | Perform useful work, disclose missing independence, do not claim independent completion/release |
| No Git and no browser in a UI project | Use file evidence and available checks; required visual paths remain unverified |
| Existing unrelated dirty files | Preserve baseline; never clean the tree to satisfy a review assertion |
| Delegated task finishes | Integrate bounded result into existing records, no nested team or per-agent document collection |
| User asks status twice | Report actual state; do not increment CARRIED for status questions |
| Project rule conflicts with method | Respect explicit user authority and resolve only the undecided conflict; continue unaffected work |

Technical acceptance: repeated setup/refresh preserves project-owned bytes; foreign instructions/hooks conflict before writes; all command copies reference the same method sections; pointers are relative to their containing file; method switching removes only known method artifacts; failed checks cannot be recorded as successful integration.
